# 通知发送与恢复

上传版本和通知记录在同一数据库事务内提交。下载事件记录实际请求的版本，不再使用后台执行时的最新版本。通知记录的唯一键防止上传完成重试重复登记；数据库行锁保证重复后台任务只领取一次发送。

每次发送携带固定 `Idempotency-Key` 和 `X-Zealot-Delivery-ID`。领取后先提交 `sending`，再发 HTTP。2xx 记为 `sent`；超时、非 2xx、后台进程中断等无法判断接收方是否已处理的情况记为 `uncertain`，不自动重发。发送前渲染失败记为 `failed`。这保证自动处理不会因未知响应盲目重复发送，但可能需要人工处理漏发；不声称 HTTP 外部系统具有 exactly-once 语义。

渠道 webhook 旁的“通知记录”显示状态，并允许有该渠道及共享 webhook 管理权限的用户手动重试失败/待核实通知。手动重试沿用通知 ID，界面提示可能重复；接收方应按该 ID 去重。任务领取时重新检查用户和渠道授权及 webhook 是否仍启用。日志和记录不保存目标 URL、请求正文或响应正文。

每分钟对账补排仍为 pending 的记录；超过十分钟的 sending 标记待核实。数据库恢复必须先停止 worker，使用 `ZEALOT_RECOVERY_MODE=true` 启动维护命令，并调用 `WebHookDelivery.suppress_before!(恢复切点)` 抑制备份内旧通知。还须清理旧版 `AppWebHookJob` 队列及其他旧任务；完整恢复工具负责执行，不能仅关闭这个开关就开放恢复后的服务。

恢复前已经发出的 HTTP 请求无法撤回。发送结果未知的记录不能自动恢复为 pending。旧版兼容作业缺少明确版本 ID 时只在首次转换时选取版本；恢复流程应抑制这些旧作业，新的调用路径均明确绑定版本。
