# 上传恢复与对象清理

`ReconcileUploadsJob` 每 5 分钟检查上传状态。已上传但停止更新心跳的任务会重新排队；解析任务使用 PostgreSQL advisory lock 防止同一会话并行发布。自动解析总尝试次数最多 3 次。手动重试与失败过期使用同一会话行锁。

分片会话超过其 24 小时期限并再经过 1 小时宽限后，会中止分片并标记过期。失败解析在最近一次更新后保留 7 天重试窗口，随后标记过期。过期不会立即删除对象，而是开始对象保留期。

`ReconcileStorageJob` 每天检查存储配置，只处理配置 prefix 下 `objects/<UUID>.<扩展名>` 的系统生成 key。其他命名或目录不受这项孤立对象扫描影响。

- 创建分片已在云端成功、但上传 ID 未写入数据库：超过 2 天后，中止未被数据库识别的分片。任何仍关联活动上传会话的 key 都受到保护，不仅依赖 upload ID 字符串相等。
- 云端文件存在而数据库对象记录缺失：超过 2 天后登记待删除记录，开始完整保留期，不在扫描时直接删除文件。
- 数据库对象没有版本、调试文件或上传会话引用：经过宽限期后标记待删除。备份对象保留给专用备份生命周期管理。

对象保留期为 `max(ZEALOT_OBJECT_RETENTION_DAYS, ZEALOT_DATABASE_RETENTION_DAYS + 7)`，默认 37 天和 30 天。`PurgeStoredObjectsJob` 只删除到期的待删除对象，且再次检查当前数据库引用。一个存储连接故障不会阻断其他存储的清理。

设置 `ZEALOT_RECOVERY_MODE=true` 会停止这几个恢复/清理任务及上传发布。恢复整个系统还需要禁用其他业务副作用并执行数据库与对象对账；不能仅凭这个开关宣称完整恢复流程已经实现。

MinIO 有一项兼容性限制：`ListMultipartUploads` 不提供标准的前缀级枚举，而要求完整对象 key。[MinIO 官方问题记录](https://github.com/minio/minio/issues/13246)。本实现保留 S3/R2 前缀扫描，并在空列表时回退到数据库已知 key 的精确查询；也实测到 MinIO 列表与创建接口的 upload ID 表示不同，因此活动 key 独立受保护。

如果 MinIO 连对象 key 的数据库记录也已丢失，应用无法通过这个接口发现该未完成分片，必须由存储端的未完成分片生命周期规则兜底。部署验收需要单独验证生产 R2 的前缀扫描及生命周期权限，不能用 MinIO 精确查询测试代替。

## 解析下载限制

解析所需的 S3 文件采用流式下载。`ZEALOT_PARSER_MAX_FILE_BYTES` 设置单个下载的最大字节数，默认 20 GiB，必须为正整数。直传任务同时使用会话中记录的预期大小作为更严格的上限：超出时立即停止接收，不将超限数据写入文件；不足时拒绝进入解析。未记录大小的历史对象仍受配置上限保护。修改此限制不会改变上传协议的 20 GiB 上限，过低的解析限制会导致较大上传进入失败状态。

下载完成、网络异常、超限或后续解析异常都会清理下载临时文件。元数据校验的 SHA1 改用流式计算，提取元数据失败也会调用解析器清理方法。

单文件下载上限之外，直传解析现在使用独立子进程，并限制运行时间、CPU/内存、文件大小和解析并发；任务临时目录统一监测与清理。具体配置、ZIP 检查和总临时空间监测的边界见 [独立解析进程](parser-workers.md)。
